# Reject token-lifetime and SMTP settings that cannot work together

The backend loads its configuration through `app.core.config.Settings`. Today it accepts several combinations where each value is valid alone but the combination is not. The app starts normally and only misbehaves later:

- `ACCESS_TOKEN_EXPIRE_MINUTES` or `EMAIL_RESET_TOKEN_EXPIRE_HOURS` can be zero or negative. Tokens then expire as soon as they are issued, so logins or password resets fail with no clear cause.
- A password-reset token (`EMAIL_RESET_TOKEN_EXPIRE_HOURS`, in **hours**) can be set to outlive a normal login session (`ACCESS_TOKEN_EXPIRE_MINUTES`, in **minutes**). A reset link is a credential that bypasses the password, so it must never stay valid longer than a session.
- `SMTP_TLS` (STARTTLS) and `SMTP_SSL` (implicit TLS) can both be enabled. These modes exclude each other, and sending mail fails at runtime.

Make `Settings` reject these combinations when it validates, so a misconfigured deployment fails at startup.

Requirements:

1. `ACCESS_TOKEN_EXPIRE_MINUTES` must be strictly positive (greater than 0). Zero or a negative value must be rejected, and the error must name `ACCESS_TOKEN_EXPIRE_MINUTES`.
2. `EMAIL_RESET_TOKEN_EXPIRE_HOURS` must be strictly positive. Zero or a negative value must be rejected, and the error must name `EMAIL_RESET_TOKEN_EXPIRE_HOURS`.
3. When both lifetimes are positive, the reset-token lifetime converted to minutes (`EMAIL_RESET_TOKEN_EXPIRE_HOURS * 60`) must not be greater than `ACCESS_TOKEN_EXPIRE_MINUTES`. **Boundary rule: equal values are allowed.** For example, 2 hours with 120 minutes is valid, and 2 hours with 119 minutes is rejected. 4. Setting `SMTP_TLS` and `SMTP_SSL` both to true must be rejected, and the error must name both `SMTP_TLS` and `SMTP_SSL`. Either one alone, or neither, stays valid.
5. When several of these problems occur together, one error must name **every** offending variable, not only the first one found.
6. Rejection means that constructing `Settings` raises a `ValueError`. Pydantic's `ValidationError` counts.
7. The shipped defaults (8-day access token, 48-hour reset token, TLS on and SSL off) must still validate, and the existing test suite must still pass.

# Reject passwords built from the user's own identity

User accounts are created from the `app.models.UserCreate` schema. This happens when an admin creates a user, when someone signs up (the signup payload is converted into a `UserCreate`), and when the first superuser is bootstrapped. Each field is checked separately. That means `email="marigold@example.com"` and `password="Marigold2024"` both pass, even though together the password is just the address with a few characters added. These accounts get taken over by simple credential-stuffing, and nobody notices until much later.

`UserCreate` must reject this combination when the schema validates it, and the error must name both fields involved.

## Rules

All comparisons ignore case.

1. **Email local part.** The local part is everything before the last `@` of `email`. If it is **3 or more characters** long, `password` must not contain it as a substring. Local parts shorter than 3 characters are not checked.
2. **Full name.** Strip leading and trailing whitespace from `full_name`. If the result is **3 or more characters** long, `password` must not contain it as a substring. A `full_name` that is `None`, or shorter than 3 characters after stripping, is not checked.
3. **Equal-values boundary.** A password that is *equal* to the local part or to the stripped full name (ignoring case) counts as containing it and is **rejected**. A local part or full name of exactly 3 characters is checked; one of 2 characters is not.

## Error behaviour

- A rejected combination makes constructing or validating `UserCreate` raise a pydantic `ValidationError`. This includes `UserCreate.model_validate(...)` on a signup payload.
- The error message must name both fields involved: `password` and `email` for rule 1, `password` and `full_name` for rule 2.
- If both rules are broken at once, a single error must name `password`, `email` **and** `full_name`.

## Unchanged behaviour

- Valid combinations still validate exactly as before. This includes users with no `full_name` and the default `is_active` / `is_superuser` values.
- The existing field-level limits (such as password length 8–128) stay as they are.
- The repository's existing test suite must keep passing.

Miniflux reads its settings from a `KEY=value` configuration file (`miniflux -config-file ...`, loaded by the config parser's `ParseFile`). Operators and tooling often need to change one setting in that file, for example to flip `LOG_LEVEL` during an incident. Today there is no writer for this file. Ad-hoc scripts rewrite it from the parsed options, and that loses data. Comments and keys Miniflux does not know about disappear. An explicitly set value that equals the default is dropped, so it silently follows future default changes. An explicit empty value turns into "unset". A crash half-way through leaves a truncated file.

Add a writer to package `internal/config` (`miniflux.app/v2/internal/config`) that makes load, modify, save lossless:

```
func UpdateConfigFile(filename string, set map[string]string, unset []string) error
```

## Behaviour

1. **Everything you did not ask to change is preserved byte for byte.** This covers comment lines (first non-blank character `#`), blank lines, lines without a key, keys unknown to Miniflux, their order, their spacing and the presence or absence of a final newline. A line is a setting when, after trimming, it does not start with `#` and contains `=` at a position greater than 0. Its key and value are the trimmed text before and after the first `=`. These are the same rules the file parser uses.
2. **Set.** For every key in `set`, the first line holding that key is replaced by `KEY=value` (no spaces). Later duplicate lines for that key are removed, so the file ends up with exactly one effective value. If the existing (trimmed) value already equals the requested value, keep the original line exactly as it was. Keys from `set` that are not yet in the file are appended at the end as `KEY=value`, one per line, in ascending key order.
3. **Explicit values are written explicitly.** A value equal to Miniflux's default (for example `LOG_LEVEL=info`) is still written. An empty string writes an explicit empty value, `KEY=`. That is not the same as removing the key.
4. **Unset.** Every line for a key listed in `unset` is removed. Unsetting a key that is not present changes nothing.
5. **No-op.** If the resulting content is identical to the current content (for example `set` and `unset` are both empty, or every value already matches), the file is not rewritten. If the file does not exist in that case, it is not created.
6. **Missing file.** A missing file is treated as empty and is created when there is something to write, with permissions `0600`. Content written to a new or previously empty file ends with a newline. If the existing file ended with a newline, the result does too. If it did not, the result does not either.
7. **Permissions.** When an existing file is rewritten, its permission bits are kept.

## Rejection and failure safety

`UpdateConfigFile` must return a non-nil error and leave the file **exactly as it was**, with no leftover temporary files next to it, when:

- a key in `set` or `unset` is empty or contains a character other than ASCII letters, digits and `_` (for example `BAD KEY` or `A=B`);
- a value contains a line break (`\n` or `\r`), because that would inject extra settings into the file;
- a value starts or ends with whitespace, because the parser trims it and the value could not round-trip;
- the same key appears in both `set` and `unset`;
- the resulting configuration is rejected by the configuration parser;
- reading, writing, syncing or replacing the file fails. The new content must be written to a temporary file in the same directory and then atomically renamed over the original, so a failed save never leaves a truncated or mixed file.

A file produced by `UpdateConfigFile` must still load with the parser's `ParseFile`. The existing behaviour of the configuration parser is unchanged, and the existing test suite must still pass.

# Export environment settings into the configuration file without losing anything

Operators who move a Miniflux deployment from environment variables to a configuration file (or keep both in sync) need to write the current environment settings into an existing config file. Doing this by hand or with ad-hoc scripts loses data. Comments and keys the script doesn't know about disappear. Values that equal the default, or are explicitly empty, are dropped and later read back as something else. Values get normalised (`yes` becomes `true`). An interrupted write leaves a truncated file.

Add a lossless merge-writer to package `internal/config` (`miniflux.app/v2/internal/config`):

```go
func ExportEnvironmentToFile(filename string, environ []string) error
```

`environ` uses the `KEY=VALUE` form that `os.Environ()` returns. A value is everything after the first `=`.

Requirements:

1. **Only Miniflux settings are exported.** An entry is used only if its key is an option the configuration parser knows about (for example `LOG_LEVEL`, `POLLING_FREQUENCY`, `RUN_MIGRATIONS`, `OAUTH2_CLIENT_ID`). All other entries (`PATH`, `HOME`, …) are ignored. If the same key appears more than once, the last one wins.
2. **Nothing in the existing file is dropped.** Comment lines (`#`), blank lines, keys Miniflux doesn't know and settings not present in `environ` stay byte for byte, in their original order.
3. **Changing one field changes only that field.** An assignment line counts as a setting when, after trimming, it isn't empty, doesn't start with `#` and has a non-empty key before the first `=`. Keys and values are compared after trimming surrounding whitespace.
   - If a key from `environ` is already in the file with the same value, its line is left untouched (original spacing included).
   - If the value differs, the line is rewritten as `KEY=VALUE`. A trailing `\r` on that line is kept.
   - Keys from `environ` that aren't in the file are appended at the end as `KEY=VALUE` lines, in alphabetical order by key.
4. **Explicit values are kept verbatim.** A value equal to Miniflux's default is still written. An explicitly empty value is written as `KEY=` and must not be skipped or replaced. Values are never normalised or converted: `RUN_MIGRATIONS=yes` stays `yes`, and `POLLING_FREQUENCY=15` stays `15`.
5. **Load then save with no change is a no-op.** If nothing changes, the function returns `nil` and does not rewrite the file. A file that doesn't end in a newline, or uses `\r\n` line endings, stays byte-identical.
6. **When the file is written**, lines are joined with `\n` and the content ends with exactly one trailing `\n`. If the original file had no trailing newline, appended keys go on new lines after the last existing line.
7. **A failed save keeps the previous record.**
   - If any exported value contains a line break (`\n` or `\r`), return an error that names the key, and don't touch the file.
   - If the parser rejects the merged settings, return an error and don't touch the file.
   - The new content is written to a temporary file in the same directory and then renamed over the target. On failure, the original file stays intact and no temporary file is left in the directory.
8. **Permissions:** an existing file keeps its permission bits. A file that doesn't exist yet is created with mode `0600`. If the file exists but can't be read, return an error.
9. The result must be loadable with the existing configuration file parser (`NewConfigParser().ParseFile(filename)`).
10. Existing configuration parsing behaviour and the repository's existing test suite are unchanged.

# Accept JSON arrays for list settings and reject malformed list values

Some Miniflux settings hold a list of values, for example networks or resource types. Today they only work as a comma-separated string such as `10.0.0.0/8, 192.168.0.0/16`. Operators often write these values as JSON arrays instead, for example `["10.0.0.0/8","192.168.0.0/16"]`, because that is how their Helm values, Compose files or secret managers render lists. The parser then splits that string on commas without complaint. The service ends up with list items such as `["10.0.0.0/8"` and `"192.168.0.0/16"]`. Nothing fails at startup, but the setting quietly stops working, for example an allow-list that matches nothing. A truncated or malformed array such as `["10.0.0.0/8",` is also accepted without any error.

Make every list-valued setting accept both spellings, and fail loudly on a list value that is clearly broken.

## Requirements

All of this lives in package `internal/config` (`miniflux.app/v2/internal/config`). Startup parses the options with `NewConfigParser()` and then the parser's line or environment parsing, and calls `Validate() error` on the resulting options right away. The new behaviour must be in place once both steps have run.

1. **JSON array spelling.** For every option whose value type is the string-list type, a value that starts with `[` (after trimming surrounding whitespace) must be read as a JSON array of strings. The parsed list must be exactly what the equivalent comma-separated spelling gives. Each item has its surrounding whitespace trimmed, empty items are dropped and items keep their order. For example, `["10.0.0.0/8", "192.168.0.0/16", "172.16.0.0/12"]` and `10.0.0.0/8, 192.168.0.0/16,172.16.0.0/12` must give the same three-item list.
2. **Empty array.** `[]` must give an empty list (length 0), not a one-item list.
3. **Malformed lists are rejected.** If a list value starts with `[` but is not a valid JSON array of strings, `Validate()` must return an error. This covers unterminated arrays, trailing garbage and non-string elements such as `[1, 2]`. The error message must contain the setting's key (for example `METRICS_ALLOWED_NETWORKS`) and the offending value exactly as written, after trimming surrounding whitespace.
4. If the setting has a value validator, the items decoded from a JSON array must still pass that validator, judged as their comma-separated equivalent. On failure, return an error naming the key and the value.
5. **Unchanged canonical behaviour.** Comma-separated values, defaults and every other setting type behave exactly as before. A default configuration must still validate.
6. The existing test suite still passes.
